# Release Test Notes - 0.5.6

Date: 2026-09-20

## Scope

mcu-serial transport link (XIAO-C5 USB-Serial/JTAG -> CAN bridge): unified
routing and link-status monitoring, across all four frontends and all
classic-CAN vendors. No CAN-FD change (hexfellow remains socketcanfd-only).

## Key Changes

- `Transport`/`open_transport`/`TransportParams` in `motor_core::bus` as the
  single `CanBus` dispatch; motor_abi, Python CLI, motor_cli, ws_gateway all
  route through it instead of per-vendor constructors.
- mcu-serial enabled for damiao / robstride / myactuator / hightorque in
  every frontend; hexfellow rejected (CAN-FD only).
- `McuSerialBus::recv` decodes the MCU-pushed STATUS frame (id `0x1FFFFFEF`,
  DLC=8) into `MotorError::BusStatus` carrying state/flags/TEC/REC/tx_failed/
  rx_dropped, so bus-off / TX-failure / RX-drop / stream-corruption surface
  as a structured error instead of a bare recv timeout.
- `scan.py` robstride/myactuator/hightorque scan functions use
  `_open_controller` (so `--transport mcu-serial` / `--serial-port` apply) and
  `_bus_hint` for accurate headers.

## Hardware-in-the-Loop (XIAO-C5 + classic CAN motor)

- Connect a XIAO-C5 on `/dev/ttyACM0` and a classic-CAN motor (damiao /
  robstride / myactuator / hightorque) on the bus.
- `motorbridge-cli scan --vendor <v> --transport mcu-serial --serial-port
  /dev/ttyACM0 --serial-baud 921600 --start-id 1 --end-id 16 --timeout-ms 100`
  for each vendor: confirm hits on present motors and `scan done: N motor(s)`.
- Trigger a bus fault (drop CAN termination, or power a motor off mid-scan):
  confirm a `BusStatus` error surfaces with a non-empty flag list rather
  than a bare timeout.
